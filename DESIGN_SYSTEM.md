Source of truth: [design.md](design.md) (generated by Stitch). This document audits that file, resolves its internal inconsistencies with documented reasoning, and converts it into tokens and components ready to implement. Nothing here invents a new visual language — every token traces back to a value in `design.md`.

## Part 1 — Design Audit

### 1.1 Critical inconsistency found (read this first)

`design.md` contains **two color systems that don't fully agree**:

1. A YAML frontmatter block (`colors:`) — a full Material Design 3–style token export (surface/on-surface/tertiary-fixed/etc., ~35 tokens).
2. A prose **"Colors"** section — a small, named palette: warm white background `#F7F7F3`, near-black `#111111`, Electric Blue `#4D7CFE`, Acid Lime `#C8F31D`, Soft Coral `#FF6B5E`, "gradients strictly prohibited."

**They are not contradictory brands — the frontmatter is a systematic M3 expansion of the same core palette**, evidenced by direct matches:
- `tertiary-fixed: #c8f31d` = exactly Acid Lime `#C8F31D`.
- `secondary: #1151d3` / `secondary-container: #3a6bed` ≈ Electric Blue `#4D7CFE` (same hue family, M3 shifted it for its own contrast math).
- `surface / background: #faf9f5` ≈ warm white `#F7F7F3` (near-identical, off-white paper tone).
- `on-surface: #1a1c1a` ≈ near-black `#111111` (same intent, different exact value).
- `primary: #000000`, `on-primary: #ffffff` — consistent with "Monochromatic Core."

**Resolution (documented decision, not a silent change):**
- The **prose section is authoritative for the five named brand colors** (background, near-black, electric blue, acid lime, soft coral) because it is explicit, intentional, and gives usage rules ("used exclusively for...", "reserved for..."). These are the values implemented below.
- The **frontmatter is used only to fill gaps the prose doesn't cover** — specifically `error`/`on-error` (no error color is named in prose, and `#ba1a1a`/`#ffdad6` are reasonable, low-saturation, print-plausible values) and the `outline-variant` border tone at low opacity, which aligns with the prose's own "#111111 at 15% opacity" border spec.
- Frontmatter tokens that conflict with prose rules are **dropped**, not merged: e.g. frontmatter's `secondary-fixed`, `inverse-*`, `*-container` families duplicate M3 concepts (containers, inverse surfaces) that `design.md`'s prose never asks for and that would reintroduce visual noise the brief explicitly rejects ("strictly flat," "no gradients"). Keeping them would silently expand the palette beyond the 5-color system the brief describes as deliberate.

This is the one place `design.md` required interpretation rather than direct extraction — documented here per the brief's own instruction (§1.8: "if something needs to change... document the reason").

### 1.2 Visual Language
- **Aesthetic**: "Technical Editorial" / "Technical Minimalist" — Swiss International Style structure + software-engineering precision.
- **Style**: Print-first, flat, monochrome-dominant with two sparing accent colors and one rare tertiary accent.
- **Visual hierarchy**: Typography carries hierarchy, not color or elevation. Large display type is treated as a graphic element, deliberately allowed to clip.
- **Density**: Spacious. Whitespace is a primary design tool, not a gap-filler.
- **Spacing philosophy**: Large, deliberate "stack" gaps (128px between major sections) create an "issue/chapter" rhythm.
- **Layout philosophy**: Strict 12-column grid, asymmetric — content deliberately avoids centering.
- **Interaction style**: Minimal, functional, non-decorative. Hover states are solid color-fills or small (2px) translations — never shadow/scale/glow.

### 1.6 Layout
- **Grid**: 12-column, asymmetric (content in first 4 columns, imagery/metadata in the rest, or reversed) — desktop/tablet.
- **Mobile**: collapses to 4-column grid, 1rem (16px) margins (overrides `margin-page` on mobile — explicit in `design.md`).
- **Section spacing**: `stack-xl` (128px) between major sections.
- **Breakpoints**: not numerically specified in `design.md` beyond "mobile" vs. the 12-col desktop grid. §1.7 documents the derived breakpoint values (standard Tailwind scale, chosen for zero-ambiguity implementation).

### 1.7 Documented gaps requiring a technical decision
These values are *not* present in `design.md`. Each is resolved here with reasoning so the decision is traceable, not silent:

| Gap | Decision | Reasoning |
|---|---|---|
| Micro-spacing scale (< 32px) | `space-1: 4px, space-2: 8px, space-3: 12px, space-4: 16px, space-6: 24px` | Standard 4px base grid, divides evenly into the existing `gutter` (24px) and `stack-md` (32px) values — stays consistent with the existing scale rather than introducing an unrelated ratio. |
| Breakpoints | `sm: 640px, md: 768px, lg: 1024px (12-col grid activates), xl: 1280px` | `lg` is where "mobile 4-col vs desktop 12-col" switches, matching Tailwind defaults so no custom breakpoint config is needed (avoids unnecessary config per [architecture.md](architecture.md)). |
| Monospace typography | Not implemented in v1 | No code snippets are part of the defined content (see [scope.md](scope.md)); revisit only if a project entry needs inline code display. |
| Success/Warning colors | Reuse Electric Blue / Soft Coral (§1.3) rather than new hues | Keeps the 5-color discipline the brief mandates ("Logic: solid fills only... maintain editorial integrity"). |
| Focus ring | 2px solid Electric Blue `#4D7CFE`, 2px offset | Not specified in `design.md`; Electric Blue is already the defined "interactive state" color, so focus reuses it rather than introducing a 6th color — required for WCAG 2.1 AA keyboard-visibility regardless of source design. |
| Shadow tokens | **None** — intentionally omitted | `design.md` §"Elevation & Depth" explicitly states depth is "never through shadows or blurs." A `--shadow-*` token set is not created; this is a deliberate absence, not an oversight. |
| Z-index scale | `z-nav: 40, z-dialog: 50, z-overlay: 45` | Not specified; minimal scale needed only for the mobile nav and the `?` shortcuts dialog — kept small since `design.md` says z-index should only be used for "intentional overlapping," not general layering. |
| Mobile `display-xl`/`display-lg` sizes | `display-xl-mobile: 112px` (150×0.75), `display-lg-mobile: 72px` (96×0.75) | `design.md` §"Mobile" only says to "reduce the size of `display-xl` significantly" without a number, and doesn't mention `display-lg` at all. `design.md` does give one concrete mobile pairing — `headline-lg` 64px → `headline-lg-mobile` 48px, a 0.75 ratio — so that same ratio is applied to the two display sizes rather than picking an arbitrary new number. Weight/line-height/letter-spacing are left unchanged between breakpoints for these two sizes since `design.md` doesn't call out any change to them, only size. |
| Navigation `backdrop-blur` | Sanctioned exception to the "never blurs" rule above — `bg-background/80` + `backdrop-blur-sm` on the sticky nav bar | Introduced by the updated Hero design the user supplied directly 2026-08-25 (`stitch-design/html/hero-v2-availability.html`, not the original `design.md`/live Stitch project). This is a translucency effect for a fixed/sticky surface reading content scrolling underneath it — not a depth/elevation cue (no shadow, nothing is "lifted"), so it doesn't contradict the *reasoning* behind "never through shadows or blurs" (that rule exists to keep depth flat, not to ban blur outright), but it is new — the original `design.md` never asked for this. Scoped to the nav bar only; not applied elsewhere. |

### 1.8 Shape
- **Corner radius**: `0px` default for all major components (cards, buttons, sections).
- **Subtle radius**: `4px` (`radius-sm`) — small interactive elements only (inputs, tags). Never exceeded.
- **Prohibited**: pill shapes, circles (except small status dots).

### 1.9 Components identified in `design.md`
Directly specified: Button (primary/secondary), Tag, Input Field, Card, List (with hairline divider + arrow-up-right hover), Icon (Lucide, 2px stroke).
Implied by the IA analysis in [scope.md](scope.md) but not visually specified — built using only the tokens above, no new visual language: Navigation, MobileNavigation, Section wrapper, Container, Heading, Text, Divider, SocialLink, ProjectRow (a List item), SkillTag (a Tag), Footer.

### 1.10 Interaction states
| State | Spec | Source |
|---|---|---|
| Button primary hover | background → Electric Blue | prose |
| Button secondary hover | fills with Acid Lime | prose |
| List row hover | arrow-up-right icon translates 2px | prose |
| Input active/focus | bottom-border color → Electric Blue | prose |
| Disabled | **Not specified — gap.** Derived: `#111111` at 30% opacity, no pointer events. | derived, needs visual sign-off during implementation |
| Loading | **Not specified — gap.** No loading states are needed in v1 (no forms/async data, see [scope.md](scope.md) Out of Scope). | n/a |

**Resolved: Button primary hover contrast.** White text (`#FFFFFF`) on the literal Electric Blue hover fill (`#4D7CFE`) computed to 3.73:1 — below WCAG AA's 4.5:1 for normal-size text (Button renders at 17px/regular). Found during the 2026-08-25 QA pass and initially left open (this is the one place `design.md`'s prose is explicit about the fill color, "On hover, the background shifts to Electric Blue," so changing it wasn't done unilaterally). **Fixed 2026-08-25 per explicit user request**: Button's primary hover/active fill now uses `--color-accent-primary-text` (the same darkened-to-6.44:1-with-white-text blue already used for standalone link text) instead of `--color-accent-primary`. `--color-accent-primary` itself is untouched for focus rings and anywhere else it's used as a fill with dark/near-black text on top (contrast math differs there).

**Resolved: standalone accent-primary text contrast.** Electric Blue as ordinary link/label text on the `#F7F7F3` background computes to 3.47:1 at normal sizes (16–17px) — fails AA. Unlike the Button case, `design.md` never specified a hex for standalone text color, only "inline text links use accent-primary color" — so this was a gap, not an instruction to override. Resolved with `--color-accent-primary-text: #0144fe` (same hue, darkened to 6.0:1) in `globals.css`, used by `Link`/`SocialLink` and `Navigation`'s persistent active-section indicator. `--color-accent-primary` itself is untouched for fills, focus rings, and the transient nav-link hover state (`hover:text-accent-primary`) — those aren't the resting/persistent presentation this fix targets.

### 1.11 Responsive design
- Explicit: mobile collapses to 4-col/1rem margins; `display-xl` must be reduced so ≥2 characters fit viewport width on mobile.
- Not explicit (documented in §1.7): exact breakpoint pixel values, tablet-specific grid behavior (assumed: tablet uses the mobile 4-col layout up to `lg` per standard breakpoint, then switches to 12-col at `lg`+, rather than an interim scale — simplest interpretation consistent with "collapse to 4-column" language, which names only two states, not three).

Flagged here because `design.md` doesn't specify on-lime text color — this is a required accessibility decision resolving a `design.md` gap (per brief §1.8).

## Part 3 — Component Inventory

Only components with a basis in `design.md` (directly specified or a direct structural implication of the IA in [scope.md](scope.md)) are included. No component from the brief's illustrative list is added speculatively (no Select, Dropdown, Checkbox, Avatar, Badge — none are implied by the content or design).

### Button
- **Purpose**: primary actions (Hero CTA, Contact) and secondary actions.
- **Variants**: `primary` (solid `#111111` fill, white text, hover → Electric Blue fill), `secondary` (1px `#111111` border, no fill, hover → Acid Lime fill + near-black text).
- **Sizes**: one size in v1 (design specifies no size scale) — `md`, `padding: var(--space-3) var(--space-6)`.
- **States**: default, hover, focus (2px Electric Blue ring, 2px offset), disabled (30% opacity, §1.7 gap), active (no distinct spec — reuse hover fill at 90% opacity).
- **Radius**: `--radius-none` (0px, per shape rules).
- **Accessibility**: native `<button>`/`<a>`, visible focus ring always (never `outline: none` without replacement), min 44×44px hit target on touch.
- **Tokens used**: `--color-text-primary`, `--color-on-primary`, `--color-accent-primary`, `--color-accent-utility`, `--color-on-accent-utility`, `--font-family-body`, `--font-size-body-md`.

### IconButton
- **Purpose**: mobile nav toggle, shortcuts-dialog trigger.
- **Sizes**: 44×44px hit area (icon itself 20–24px, 2px stroke per Lucide spec).
- **States**: default, hover (subtle fill or border, not shadow), focus, active.
- **Tokens used**: `--color-border`, `--color-text-primary`, `--radius-sm`.

### Tag
- **Purpose**: skill labels, project stack labels, status/featured indicators.
- **Style**: rectangular, 1px `--color-border`, no rounding (or `--radius-sm` only if used as a small interactive filter tag — not planned for v1), metadata typography (`--font-size-metadata`, uppercase, `--letter-spacing-metadata`).
- **Variants**: `default` (outline only, as above) and `accent` — solid `--color-accent-utility` (Acid Lime) fill + `--color-text-primary` border + `--color-on-accent-utility` text, per design.md's own "background fills for small tags/labels" use of that color. Used for Work's "Featured" tag and Hero's "Available for Work" status tag (the latter added 2026-08-25, matching the updated Hero design).
- **States**: static (skills), hover only if ever made interactive (not planned v1).
- **Tokens used**: `--color-border`, `--color-text-secondary`, `--color-accent-utility`, `--color-text-primary`, `--color-on-accent-utility`, `--font-size-metadata`, `--font-weight-metadata`, `--letter-spacing-metadata`.

### Input / TextField
- **Purpose**: reserved for a possible future contact form; not used in v1 (see [scope.md](scope.md) Out of Scope — `mailto:` only). Documented for completeness/consistency since `design.md` specifies its style.
- **Style**: bottom-border only, 1px `--color-text-primary`, active → `--color-accent-primary`.
- **Radius**: `--radius-sm` (per "small interactive elements" rule).

### Card
- **Purpose**: not required by the v1 IA (Work uses list rows, per §1.0 audit) — documented for completeness if a future section needs a bounded content block.
- **Style**: borderless, whitespace-defined, or 1px `--color-border-subtle` **top-border only**.
- **Radius**: `--radius-none`.

### List / ListRow (→ ProjectRow, ExperienceRow)
- **Purpose**: primary pattern for Work/Projects and Experience sections.
- **Style**: hairline `--color-border` divider between rows, no divider on first/last per section.
- **Interaction**: on hover, trailing Lucide `ArrowUpRight` icon translates `--motion-hover-translate` (2px) via `transform`, `transition-duration: --motion-duration-fast`.
- **States**: default, hover, focus-visible (keyboard-operable — the whole row is a single `<a>`, not a nested interactive element).
- **Responsive**: single-column stacked row on mobile; may show a secondary column (date/tag) inline on `lg`+.
- **Tokens used**: `--color-border`, `--color-text-primary`, `--color-text-secondary`, `--motion-hover-translate`, `--motion-duration-fast`.

### Navigation / MobileNavigation
- **Purpose**: section anchors (About/Work/Experience/Contact) + shortcuts-dialog entry point.
- **Desktop**: uppercase metadata-style text links (updated 2026-08-25 from body-md — see the updated Hero design), no pill/box background. Current-section indicated via bold weight + a 2px bottom border (not text-decoration) in `--color-accent-primary-text`, not a box/pill.
- **Wordmark**: `headline-lg`/`headline-lg-mobile` scale, uppercase, tight tracking (updated 2026-08-25 — was body-md scale).
- **Bar treatment**: `bg-background` at 80% opacity + `backdrop-blur-sm` (updated 2026-08-25 — see §1.7 "Navigation backdrop-blur" for why this doesn't contradict the flat/no-blur elevation rule).
- **Mobile**: full-screen Radix Dialog overlay (not hand-rolled — see §1.10-adjacent QA note), `--z-nav`, closes on `Esc` and outside-tap, focus-trapped and focus-restored automatically.
- **Accessibility**: `<nav>` landmark, current page/section via `aria-current`, mobile toggle is a real `<button>` with `aria-expanded` (managed by Radix's `Dialog.Trigger`).

### Section / Container
- **Purpose**: layout primitives, not visual components — enforce `--space-stack-xl` between sections, `--space-page-margin` / `--space-page-margin-mobile` page margins, and the 12-col → 4-col grid.
- **No visual styling of their own** (no background/border) — purely structural, per "elements sit directly on the paper" (§1.0 Elevation).

### Heading / Text / Link / Divider
- **Purpose**: typographic primitives wrapping the type-scale tokens so no component hardcodes a raw font-size.
- **Heading**: accepts a `level` (`display-xl | display-lg | headline-lg | hero-name`) mapped to the semantic HTML tag separately from visual size (so visual scale and document heading level, `h1`–`h3`, can differ — required for a correct heading outline when Hero uses `hero-name` but is still the page's single `h1`). `hero-name` (added 2026-08-25) is fluid (`clamp()`), unlike every other level's discrete mobile/desktop pair — see §1.7.
- **Divider**: 1px `--color-border`, used between list rows and optionally between major sections in place of pure whitespace where a visual break is wanted (used sparingly, per "hairline dividers between items" spec — a List usage, not a page-wide pattern).
- **Link**: inline text links use `--color-accent-primary`, underline on hover only (no persistent underline, keeps the editorial/clean text blocks the brief describes).

### SocialLink
- **Purpose**: Footer + Contact — GitHub/LinkedIn/email icons or text links.
- **Style**: IconButton or text Link depending on placement; uses Lucide icons at 2px stroke for consistency.

### Footer
- **Purpose**: closing landmark — copyright, SocialLinks, back-to-top.
- **Style**: minimal, top hairline divider (`--color-border-subtle`) separating it from Contact, no full-width fill/background.

**Note on the Beyond Mobile stack diagram**: the pulled Stitch screen for Beyond Mobile (`stitch-design/html/beyond-mobile.html`) includes a small UI/Client → API/Server → Database diagram with absolute-positioned connector arrows. This is bespoke section content specific to that screen, not a reusable design-system primitive — it should be built as one-off markup within the Beyond Mobile section, not generalized into a new component here.
